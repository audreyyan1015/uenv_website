统一环境接口，
让训练专注于训练。

UEnv 是一个训练框架无关的分布式环境执行框架，为 LLM 后训练提供统一、可扩展的 Environment 接口。

快速开始 查看系统架构

框架解耦

通过 Bridge 对接 VeRL 等训练框架，训练侧不需要感知 Worker 与环境插件细节。

分布式执行

Server 统一调度，Worker Pool 主动执行 Episode，并支持环境预热与容量扩展。

可观测可靠

围绕注册、心跳、Dispatch、Report 和 WAL 构建可追踪、可恢复的执行链路。

为什么使用 UEnv

后训练系统同时面对多种训练框架、环境类型和执行资源。UEnv 把这些差异收敛到清晰的组件边界，让算法工程师与平台工程师各自关注自己的问题。

A

算法与训练团队

使用统一 Episode 接口接入环境，把精力放在采样策略、奖励设计和训练效果上。

B

平台与环境团队

独立维护调度、Worker、环境插件与制品注册，无需侵入上层训练框架。

快速开始

当前版本没有单独的 uenv-server 进程：Server 作为 Rust 库嵌入 Adapter Core。下面的命令在同一台开发机上启动 Adapter Core、Hub 和一个 Worker。

环境要求需要 Rust 工具链、Python 3.10+，并在仓库根目录准备好 Server 与 Worker 配置。示例把 Worker 改到 50054，避开 Server admin HTTP 默认使用的 50052。
Terminal
# 1. 构建当前核心组件
cargo build -p uenv-server -p uenv-worker -p uenv-adapter-core
(cd uenv-hub && cargo build)

# 2. Terminal 1：启动 Adapter Core 与控制面
UENV_ADDR=0.0.0.0:50051 \
  UENV_CONFIG_PATH=config/server.yaml \
  UENV_SERVER_CONFIG_STRICT=1 \
  cargo run -p uenv-adapter-core

# 3. Terminal 2：启动环境注册中心
(cd uenv-hub && UENV_HUB_AUTH__REQUIRE_TOKEN=false cargo run -p uenv-hub-server)

# 4. Terminal 3：接入 Worker
UENV_SERVER_ENDPOINT=127.0.0.1:50051 \
  UENV_WORKER_LISTEN=0.0.0.0:50054 \
  UENV_WORKER_ADVERTISE_ENDPOINT=127.0.0.1:50054 \
  UENV_HUB_ENDPOINT=http://127.0.0.1:8080 \
  cargo run -p uenv-worker -- --config config/uenv-worker.yaml serve

一次环境执行的基本路径

以下是普通 Native Worker 路径。SWE Agent 和 Code Agent 走不同的资源获取与任务分发流程，见 uenv-server 页面。

1

准备请求

Bridge 将 prompt、采样参数、奖励配置与环境元数据组装为 EpisodeRequest。

2

排队并选择 Worker

Server 先取得 admission 名额，再过滤 draining、degraded、环境类型、资源、环境包和容量不匹配的 Worker。

3

执行环境

Worker 获取或拉起环境实例，完成 reset → step → close，并直接访问推理服务。

4

返回轨迹

执行结果经 ReportResult 汇总为 EpisodeResult，回到 Bridge 并进入后续训练。

配置说明

配置按组件拆分。Server 与 Worker 使用各自的运行时配置，Hub 使用 TOML，并支持环境变量覆盖。

Server 配置边界UENV_ADDR 决定 Adapter Core 的 gRPC 监听地址；当前 server.yaml 中的 port 字段不控制该监听端口。普通加载模式只在配置文件不存在时回退默认值，文件存在但内容非法仍会启动失败；设置 UENV_SERVER_CONFIG_STRICT=1 后，文件不存在也会报错。

接收训练样本

RS

uenv-server

Episode 调度与运行状态管理

uenv-server 接收 Episode 请求，控制并发，选择 Worker 或 Agent 执行路径，校验最终结果，并保存任务状态。环境的实际执行发生在 Worker 或 Agent 中，不在 Server 进程中。

基本对象

UEnv 是分布式任务执行系统：上游提交任务，远端进程执行任务，Server 负责协调执行过程。

名称在本文中的含义
EpisodeServer 调度和记录的任务单位。一次 Episode 从收到请求开始，到完成、失败、取消或超时结束。它可以包含一个或多个环境交互步骤。
Environment接收操作并返回观测、奖励和结束状态的程序。它可以实现问答、代码测试或容器化软件任务。
Worker运行 Environment 和环境插件的独立进程。Worker 向 Server 注册支持的环境类型、资源、容量和网络地址。
Bridge把 VeRL 等上游框架的数据转换成 UEnv 的 EpisodeRequest，并把 EpisodeResult 转换回上游格式。
Agent从 Server 拉取 AgentJob 并执行多步操作的外部程序，例如修改代码和运行测试。这里的 Agent 是运行时组件，不表示某个强化学习算法。
uenv-server 不是单独启动的程序仓库里的 uenv-server 是 Rust 库。真正启动的是 uenv-adapter-core；它在进程内创建 Server 状态，并把训练请求、Worker 控制面、Agent 控制面和管理接口注册到 gRPC Server。

Server 按当前代码实际执行的流程

流程节点按照当前代码中的函数调用和状态变化排列。标有“启用持久化时”的步骤仅在配置状态库后执行。

参与对象 任务 是一次需要处理的请求；Server 接收并安排任务；Worker 运行指定环境；Agent 执行修改代码、运行测试或调用工具等多步操作。
所有请求共同执行submit_episode → execute_episode_inner
  1. 规范化任务标识、运行模式和异步请求信息
  2. 查询或创建任务记录，处理重复提交和相同任务 ID 的等待调用
  3. 登记活动任务，计算截止时间并等待 Server 全局执行名额
  4. 选择 SWE Agent、Code Agent 或默认的 Native Worker 后端
选择一条执行路径
Native Worker 路径：4 个阶段Server 直接选择 Worker，并调用 Worker 执行环境
  1. 选择 Worker，并准备 lease、结果通道和派发记录
  2. 调用 Worker 启动环境执行
  3. Worker 独立回报；Server 校验身份、派发凭据和重复结果后提交结果
  4. 返回结果；临时派发错误可重试，环境失败、取消或超时直接结束
SWE Agent 路径：5 个阶段同时需要 Agent 名额和带 Runtime Gateway 的 Worker
  1. 解析 Agent Pool，同时取得 Agent 名额和匹配的 Worker
  2. 通过 Worker Gateway 创建并保存本次运行会话
  3. 生成 Agent Job，先保存再加入任务队列
  4. 等待 Agent 领取并完成，同时处理领取超时、总超时和取消
  5. 释放 Worker、关闭会话并发布最终结果
Code Agent 路径：4 个阶段只使用 ToolEnv Agent Pool，不选择 Worker，也不创建 Gateway 会话
  1. 解析 ToolEnv Agent Pool 并等待可用名额
  2. 登记活动任务，把无 Gateway 的 Agent Job 加入内存队列
  3. Agent 领取并执行；Server 同时处理领取超时、总超时和取消
  4. 清理活动记录和 Job，并发布最终结果
执行后端返回
执行后端返回以后这一段只适用于启用了持久化和 EpisodeCoordinator 的提交入口
  1. 检查结果大小并提交最终任务记录
  2. 通知相同任务 ID 的等待者，移除协调记录并返回结果

用一个普通任务看完整流程

假设上游要执行一个问答任务：“2 + 3 等于多少？”在默认的 Native Worker 路径中，程序会经历下面这些步骤。

1

上游提交任务

Bridge 把题目、任务 ID、环境类型和超时时间等信息整理成 EpisodeRequest，交给同一进程中的 Server。

2

Server 登记任务

Server 检查这个 episode_id 是否已经出现过。若同一个任务正在执行，新调用会等待原来的执行；若同一 ID 对应的内容不同，Server 会拒绝它。

3

等待并发许可

Server 使用 semaphore 实现 admission 并发控制。请求必须先取得 permit；等待期间如果达到 Episode deadline 或收到取消信号，请求不会进入执行后端。

4

选择 Worker

Server 找到支持该环境、资源足够、仍有空闲容量且心跳正常的 Worker，并为这次分配临时占用一个名额。

5

下发任务

Server 为本次分发生成 lease、token 和过期时间，先把分发意图写入状态库，再调用 Worker 的 DispatchEpisode。

6

Worker 执行环境

Worker 调用环境插件的 reset、step 和 close。它可以在执行流中发送进度，但最终结果通过独立的 ReportResult 接口回报。

7

Server 保存并返回结果

Server 验证回报确实属于这次分发，提交终态并通知等待者。Adapter Core 再把结果返回给 Bridge，上游得到答案、轨迹和分数。

几个容易混淆的机制

代码中的词作用具体行为
admission限制已经进入执行流程的 Episode 数量请求异步等待 semaphore permit；完成、取消或失败后释放 permit。
reservation记录 Server 已分配但 Worker 心跳可能尚未反映的负载选择 Worker 时增加 reserved_load，执行结束时减少；有效负载取 reservation 与 Worker 上报负载的较大值。
lease 与 token把最终结果绑定到某一次具体分发每个 attempt 生成新的 lease ID 和随机 token；ReportResult 的 Worker、lease 和 token 必须与待回报记录一致。
server_epoch区分 Server 重启前后的进程实例Server 启动时生成 epoch；Worker 心跳和结果携带该值，旧实例的数据会被识别。
idempotency_key处理 Worker 对同一结果的重复回报同一 key 和同一回报返回已保存的处理结果；同一 key 对应不同内容时返回冲突。
outbox保证已提交终态的完成事件可以在重启后继续发布终态事务同时插入未投递事件；恢复流程读取未投递记录，发布后再标记 delivered。
请求去重和结果去重不是一回事提交 Episode 时，Server 使用 episode_id + request_checksum 判断“是不是同一个任务”。Worker 回报结果时，Server 使用 ReportResult.idempotency_key 判断“是不是同一次结果重传”。

Server 怎样选择 Worker

当前调度策略是 round_robin，也就是在合格的 Worker 之间轮流选择。它不是在所有 Worker 中盲目轮询，而是先做过滤：

环境能力Worker 必须声明支持请求中的 env_type，例如 qa、code 或 swe。
资源与环境包CPU、内存、GPU 等资源要满足请求；指定 EnvPackage 时，Worker 必须已经同步对应版本。
容量Worker 当前有效负载必须小于容量。有效负载取 max(reserved_load, reported_load)。
健康状态正在 draining、心跳超时或长时间有负载却没有完成任务的 Worker 不接收新任务。

为什么还有 Agent 路径

普通任务由 Worker 直接运行环境。需要反复查看文件、修改代码和运行测试的代码任务由 Agent 执行，Server 会把这类任务放入 Agent Pool。三条路径使用的资源如下：

路径什么时候使用与普通 Worker 路径的区别
Native Worker默认路径Server 直接选择 Worker 并调用 DispatchEpisode
SWE Agentenv_type=swe 且请求指定 execution_mode=agent同时需要 Agent 名额和一个 Worker Runtime Gateway session
Code Agentenv_type=code 且请求指定 execution_mode=agent只使用 ToolEnv Agent；不选择 Worker，也不创建 Gateway session

结果回报、超时和重试

Worker 的 DispatchEpisode 调用可以返回执行进度，但最终结果必须通过 ControlPlaneService.ReportResult 独立回报。Server 会检查 Worker ID、lease、token 和 epoch；这样即使网络重复发送、任务已经取消，或旧 Worker 很晚才返回，也不会覆盖正确结果。

重试也不是“失败就再跑一遍”。连接中断、模型服务临时失败或暂时没有容量可以重试；确定性的环境执行失败不会换一个 Worker 重跑，因为重复执行可能再次消耗模型调用，并产生外部副作用。

哪些状态能在重启后恢复

状态位置保存内容重启后的行为
Server 状态 SQLiteEpisode 请求和终态、dispatch、结果幂等记录、AgentJob、Gateway session、outboxServer 启动时读取并恢复等待、超时、清理和事件补发
Trajectory Store轨迹文件以及供查询使用的 EpisodeResult 索引它是独立的可选存储，不与 Server 状态库共享事务
内存运行态Worker / Agent 注册和心跳、等待通道、取消句柄、短期缓存进程退出后消失；Worker 和 Agent 必须重新注册、继续发送心跳
“持久化”不代表所有数据一起提交终态 EpisodeResult 与 outbox 事件在同一个 Server 状态库事务中提交。Trajectory Store 随后独立写入；轨迹索引写入失败不会回滚已经提交的 Server 终态。

RS

uenv-worker

环境执行与实例运行时

连接 Server 控制面，接收带租约的 Episode，在本机管理环境实例、插件进程、模型调用、预热池与执行结果回报。

主要职责

接入控制面

注册真实容量与环境能力，持续发送心跳，并在 Server epoch 变化后重新注册。

执行 Episode

校验租约和并发容量，驱动插件 reset → step → close，输出进度与最终轨迹。

运行时可靠性

通过预热池减少冷启动，通过 WAL 保存未确认结果并在重连后重放。

执行路径

1

启动并注册

加载 YAML，发现资源与环境能力，启动 Worker gRPC、指标、健康检查及心跳循环。

2

接收 Dispatch

验证 lease、token、过期时间与并发信号量，拒绝冲突或过期任务。

3

准备环境

从预热池获取实例；需要时通过 Hub resolver 同步 EnvPackage 并注册 manifest。

4

执行并回报

执行普通插件或 SWE 专用路径，先写 WAL，再调用 ReportResult，确认后清理记录。

RS

uenv-hub

环境元数据与制品注册中心

为环境、版本、接口 Schema、EnvPackage、Agent Bridge 与 Episode Stack 提供可查询、可解析、可审计的 HTTP 注册服务。

主要职责

版本与 Manifest

创建环境、发布版本、解析约束、获取接口与示例，并支持 yank 和增量同步。

包与组合交付

管理内容寻址的 EnvPackage 制品、Agent Bridge 目录和 Episode Stack 解析结果。

治理与审计

提供 token、角色、命名空间权限、限流、审计日志和发布校验。

Worker 如何使用 Hub

1

解析引用

Worker 根据 env_package_id 和 version 请求版本或 Stack 的解析结果。

2

获取同步计划

Hub 返回 manifest、接口定义、bundle digest 与需要下载的制品信息。

3

同步到本地

Worker 下载并校验制品，把本地 manifest 注册到 PluginHost 后再创建实例。
