统一环境接口，
让训练专注于训练。

UEnv 为 LLM 后训练提供统一的环境执行接口。当前已接入 VeRL，整体架构可以继续适配其他训练框架。

快速开始 查看系统架构

框架解耦

当前通过 Bridge 对接 VeRL，训练侧不需要了解 Worker 和环境插件的内部实现。

分布式执行

Server 统一调度，Worker Pool 主动执行 Episode，并支持环境预热与容量扩展。

可观测可靠

记录组件注册、心跳、任务状态和执行结果，便于查询问题并恢复部分运行状态。

为什么使用 UEnv

后训练系统同时面对多种训练框架、环境类型和执行资源。UEnv 把这些差异收敛到清晰的组件边界，让算法工程师与平台工程师各自关注自己的问题。

A

算法与训练团队

使用统一 Episode 接口接入环境，把精力放在采样策略、奖励设计和训练效果上。

B

平台与环境团队

独立维护调度、Worker、环境插件与制品注册，无需侵入上层训练框架。

快速开始

下面在一台开发机上启动 Adapter Core 和 Worker，再通过 Adapter Core 提交一个 QA Episode。完成后，你会看到请求经过 Server 调度、由 Worker 执行并返回结果。

开始前准备需要 Rust 工具链和 grpcurl。下面所有命令都从 UEnv 仓库根目录执行；50051 用于 Adapter Core，50054 用于 Worker，19090 用于 Worker 健康检查。

构建二进制并创建本地配置

这里关闭 Server 持久化，避免本地首次运行时依赖固定目录和磁盘空间配置。

Terminal
cargo build -p uenv-adapter-core -p uenv-worker --bins

mkdir -p .uenv-local
printf 'persistence:\n  enabled: false\n' > .uenv-local/server.yaml

启动 Adapter Core

Adapter Core 对外提供 gRPC，uenv-server 作为库运行在这个进程内，不需要再启动一个 Server 进程。

Terminal 1
UENV_ADDR=127.0.0.1:50051 \
  UENV_CONFIG_PATH=.uenv-local/server.yaml \
  UENV_SERVER_CONFIG_STRICT=1 \
  cargo run -p uenv-adapter-core

启动一个只运行 QA 环境的 Worker

这里显式使用仓库内的 QA Manifest 和刚构建的插件二进制，并把日志与 WAL 写到本地临时目录。

Terminal 2
UENV_SERVER_ENDPOINT=127.0.0.1:50051 \
  UENV_SCHEDULER_MODE=remote \
  UENV_WORKER_ID=local-worker \
  UENV_WORKER_LISTEN=127.0.0.1:50054 \
  UENV_WORKER_ADVERTISE_ENDPOINT=127.0.0.1:50054 \
  UENV_ENV_TYPES=qa \
  UENV_PLUGIN_DIR="$PWD/plugins" \
  UENV_QA_PLUGIN_BIN="$PWD/target/debug/uenv-math-plugin" \
  UENV_LOG_FILE="$PWD/.uenv-local/worker.log" \
  UENV_WAL_DIR="$PWD/.uenv-local/worker-wal" \
  UENV_METRICS_LISTEN=127.0.0.1:19090 \
  UENV_HEALTH_LISTEN=127.0.0.1:19090 \
  cargo run -p uenv-worker --bin uenv-worker -- --config config/uenv-worker.yaml serve

JSON
成功标志响应的第一条结果包含 "status": "completed" 和 "reward": 1。这个示例不调用模型，只用于确认 Adapter Core、Server、Worker 和 QA 插件能够协同工作；接入真实训练前仍需配置模型地址。

接入 VeRL

先确认“快速开始”的示例 Episode 能够完成，再把 Bridge 安装到现有 VeRL 训练环境。UEnv 接管的是 rollout 前的 AgentLoop；模型、数据集和训练参数仍由 VeRL 配置。

这一页不负责安装 VeRL开始前应已有一条能够启动的 VeRL 训练命令，以及可用的训练模型和 rollout 运行时。Adapter Core 与至少一个支持目标环境的 Worker 也必须已经运行。

安装 Bridge 并连接 Adapter Core

VeRL 环境
python3 -m pip install -e ./uenv-bridge

export UENV_AGENT_LOOP_CLIENT=rust_core
export UENV_ADAPTER_CORE_ENDPOINT=127.0.0.1:50051

在 VeRL 命令中启用 UEnv AgentLoop

把下面两项加入原有 Hydra 参数。配置文件必须使用绝对路径；跨机器部署时还要把 Adapter Core 地址改为 VeRL 机器可访问的地址。

Hydra overrides
actor_rollout_ref.rollout.agent.default_agent_loop=uenv_agent \
actor_rollout_ref.rollout.agent.agent_loop_config_path=/absolute/path/to/uenv/uenv-bridge/configs/uenv-agent-loop.yaml

确认模型地址来自哪里

Bridge 优先使用样本显式提供的地址或 VeRL rollout 运行时地址。如果当前 VeRL 版本无法暴露该地址，可以设置后备值：

VeRL 环境
export UENV_ROLLOUT_MODEL_ENDPOINT=http://127.0.0.1:8000/v1
export UENV_ROLLOUT_MODEL_NAME=policy-model

如果请求中仍没有模型地址，Worker 必须通过 config/uenv-worker-llm.env 或 UENV_WORKER_LLM_ENV 提供默认模型配置；否则真实 Episode 会在模型调用阶段失败。

运行后检查什么

请求对应关系每个输入样本都应返回相同 request id 对应的结果，不能缺失或重复。
AgentLoopOutput确认 response ids、response mask 和 reward_score 已返回，失败样本没有被静默当作成功。
Worker 日志确认 Episode 使用了预期环境和模型地址，并正常完成结果回报。

部署与配置

不要从完整配置表开始。先确定组件部署在哪些机器上，再处理网络地址、环境运行时和持久化目录。Bridge 的训练侧配置已放在“接入 VeRL”页面。

先确定部署方式

场景组件位置需要额外处理的内容
本地首次运行Adapter Core 与一个 Worker 在同一台机器使用回环地址、关闭 Server 持久化、只加载 QA 环境；Hub 和模型服务都不是必需项。
单机真实任务VeRL、Adapter Core、Worker 可以同机提供真实模型地址，使用可持久化的 Server 与 Worker 目录，并按资源设置并发。
多机部署VeRL、Adapter Core、Worker 分布在不同节点所有注册和回连地址必须跨机可达；再根据环境包需求决定是否部署 Hub。
仓库中的 server.yaml 不是本地开发配置它包含 /home/uenv/server-state/ 绝对路径和 10 GiB 最低可用空间检查。首次运行应使用“快速开始”生成的本地配置；部署时再换成当前机器可写、可持久化的路径。

地址之间是什么关系

配置谁使用要求
UENV_ADDRAdapter Core进程实际绑定的主 gRPC 地址；多机部署通常绑定 0.0.0.0:<port>。
UENV_ADAPTER_CORE_ENDPOINTBridge必须填写 VeRL 所在机器能够访问的 Adapter Core 地址，不能使用远端机器的 127.0.0.1。
server.endpoint / UENV_SERVER_ENDPOINTWorkerWorker 用它注册、发送心跳和回报结果；当前应指向 Adapter Core 的同一 gRPC 入口。
worker.listenWorker本机绑定地址，可以使用 0.0.0.0。
worker.advertise_endpointServerServer 回连 Worker 的地址，必须是 Server 真正能够访问的主机名或 IP，不能填写 0.0.0.0。

Worker 启动前必须确认

内容相关配置检查方式
环境是否真的可运行env.types、env.plugin_dir 和对应插件二进制环境变量Worker 日志中应出现已加载的环境类型；只声明名称但缺少 Manifest 或程序仍然无法执行。
模型地址Episode 中的 model_endpoint，或 llm.env_file / UENV_WORKER_LLM_ENV真实任务必须至少有一个有效来源；“快速开始”中的 QA 示例不调用模型，不能代替真实 rollout 验证。
本机容量worker.max_concurrent结合模型服务、CPU、GPU 和内存容量设置，不要直接照搬示例值。
日志与未回报结果logging.file、wal.dir目录必须可写；需要跨进程重启恢复时应放在持久化磁盘。
健康检查observability.metrics_listen 与 health_listen当前实现要求两个地址相同；通过该地址访问 /health 和 /metrics。

配置覆盖顺序

Adapter Core / ServerUENV_ADDR 决定主 gRPC 监听地址，UENV_CONFIG_PATH 指向 Server YAML；YAML 负责调度、超时、管理接口和持久化。
Worker命令行参数优先于环境变量，环境变量优先于 YAML/JSON，最后才使用代码默认值。
Hub Server--bind 可覆盖监听地址；其余配置按环境变量、TOML、内置默认值合并，嵌套环境变量使用双下划线，例如 UENV_HUB_AUTH__REQUIRE_TOKEN。
Hub CLI显式 --endpoint 优先，其次是 UENV_HUB_ENDPOINT / UENV_HUB_TOKEN、用户配置文件和默认值。

多机部署检查

VeRL → Adapter Core从 VeRL 节点测试 Adapter Core 主 gRPC 端口可达。
Worker → Adapter CoreWorker 必须能够完成注册、心跳和结果回报。
Adapter Core → Worker从 Adapter Core 节点测试每个 advertise_endpoint 可达；容器或 NAT 场景不能直接复用绑定地址。
持久化与密钥Server 数据库、Worker WAL、Hub 数据库和 artifact 目录使用持久化磁盘；Hub token 和模型 API key 不写入仓库。

发布与同步环境

Hub 是可选的部署组件，不在 Episode 实时执行链路中。环境作者向它发布 Environment Manifest；需要大文件或离线依赖时，运维再把已经发布的 EnvPackage 同步到 Worker 或 Agent 节点。

启动本地 Hub

下面关闭鉴权只用于本机体验。共享环境应保留默认鉴权，并由管理员提供具有相应权限的 token。

Terminal 1
cd uenv-hub
UENV_HUB_AUTH__REQUIRE_TOKEN=false cargo run -p uenv-hub-server

构建并连接 CLI

Terminal 2
cd uenv-hub
cargo build -p uenv-hub-client
export PATH="$PWD/target/debug:$PATH"
export UENV_HUB_ENDPOINT=http://127.0.0.1:8080

uenv hub status
uenv env list

连接需要鉴权的共享 Hub 时，可以设置 UENV_HUB_TOKEN，也可以执行 uenv hub login --endpoint <url> --token <token> 保存连接信息。

环境作者：发布 Environment Manifest

这条路径发布环境名称、版本、接口和运行要求等元数据。先生成项目，再编辑并校验其中的 manifest.toml。

环境作者
uenv env init myqa --template qa
cd myqa

# 编辑 manifest.toml 后执行
uenv env validate
uenv env publish --manifest manifest.toml
发布 Manifest 不会自动创建 EnvPackageuenv env publish 写入环境注册元数据；uenv env sync 消费的是另一类已经发布的 EnvPackage。两者可以描述同一环境，但不是同一个对象。

运行节点：同步已有 EnvPackage

这一步在 Worker 或 Agent 节点执行。示例使用当前目录下的可写路径；生产环境可以换成持久化的节点目录。

Worker 节点
export UENV_HUB_ENDPOINT=http://127.0.0.1:8080
export PATH="/absolute/path/to/uenv/uenv-hub/target/debug:$PATH"

uenv env sync <package-id> \
  --version <version> \
  --target-dir "$PWD/.uenv-packages" \
  --worker-version 0.1.0

CLI 会把文件写入 .uenv-packages/envs/<package>/<version>/，逐个校验 SHA-256 并写入 .synced，随后再让运行时指向这个本地目录。Agent 节点同步时还应按包声明传入相应的 --consumer，例如 --consumer toolenv-agent。EnvPackage 必须事先由运维或包发布流程写入 Hub；当前基础环境脚手架不会替你生成它。

PY

uenv-bridge

训练框架适配层

uenv-bridge 是运行在 VeRL 进程中的 Python 适配层。它在 rollout 生成前接管样本，把 prompt、采样参数和环境信息转换为 UEnv Episode；Server 与 Worker 完成生成和环境执行后，Bridge 再把结果交还 VeRL 继续训练。

Bridge 不是需要单独启动的服务UEnvAgentLoop 由 VeRL 加载并运行。它通过 gRPC 调用 uenv-adapter-core；Adapter Core 才是独立服务进程，并在进程内使用 uenv-server。

接入后发生了什么

1

把训练样本转换为 Episode

UEnvAgentLoop 在 rollout 前接收 VeRL 样本，整理 prompt、token ids、环境类型、采样参数、随机种子和奖励配置。请求只携带输入，响应由 UEnv 侧生成。

2

通过 Adapter Core 进入调度层

Bridge 使用 gRPC 提交 Episode。Adapter Core 负责网络入口，再把请求交给进程内的 Server 选择 Worker 或 Agent。

3

把结果恢复为 VeRL 输出

Bridge 按 request id 对应原始样本，把响应 token、mask、奖励、轨迹和结束原因整理成 AgentLoopOutput。

数据边界

训练侧输入prompt、采样参数、样本元数据、环境与奖励配置；Bridge 不接管 Server 和 Worker 的内部状态。
UEnv 侧输出response ids、response mask、奖励、trajectory 和 finish reason；模型生成与环境执行发生在 Worker 或 Agent。
样本对应关系结果顺序可以变化，但 request id 必须唯一对应输入样本；缺失、重复或未知 id 都会被视为错误。
当前支持范围当前 Bridge 只维护 VeRL pre-rollout AgentLoop 路径。它不负责全局任务调度，也不直接运行环境；其他训练框架适配器仍属于可扩展方向，不是现有能力。

RS

uenv-server

Episode 调度与运行状态管理

VeRL 先把训练样本交给 uenv-bridge。Bridge 将数据转换为 Episode，并通过 gRPC 发送给 Adapter Core。Adapter Core 是对外运行的服务进程，它在进程内调用 uenv-server 完成调度。uenv-server 负责控制并发、选择 Worker 或 Agent、跟踪任务状态并返回结果。

uenv-server 不是单独启动的进程uenv-server 是 Rust 库，由 uenv-adapter-core 在进程内创建和调用。对外监听 gRPC 端口的是 Adapter Core 进程。

先认识四个概念

名称含义
Episode一次完整的环境执行任务，从收到请求开始，到完成、失败、取消或超时结束。
Environment接收操作并返回观测、奖励和结束状态的程序，例如数学问答环境或代码测试环境。
Worker运行环境实例的独立进程。它向 Server 报告自己支持的环境、资源和空闲容量。
Agent执行多步工具操作的外部程序，主要用于需要修改代码、运行测试等任务。

主要职责

管理请求

识别重复请求，限制同时执行的 Episode 数量，并处理取消和超时。

选择执行资源

根据环境类型、资源、健康状态和空闲容量选择合适的 Worker；特殊任务也可以交给 Agent。

管理结果与状态

确认结果来自正确的任务分发，保存任务终态，并把结果返回 Adapter Core。

职责边界

Server 负责调度、并发控制和状态管理；Worker 或 Agent 负责实际执行；Hub 负责环境版本和制品。Server 不直接执行环境的 reset / step / close。

默认的 Native Worker 流程

Native Worker 是普通环境任务的默认路径。一次请求按下面的顺序执行：

1

接收 Episode

Adapter Core 将转换后的 Episode 请求交给 Server 模块。

2

检查并排队

Server 检查任务是否重复，并等待全局并发名额。等待超时或收到取消信号时，任务直接结束。

3

选择 Worker

Server 筛选支持该环境、资源足够、状态正常且仍有空闲容量的 Worker。

4

执行环境

Server 下发任务。Worker 准备环境实例，调用模型，执行环境步骤，并生成奖励与轨迹。

5

返回结果

Worker 单独回报最终结果。Server 完成校验和记录后，将结果返回 Adapter Core。

示例VeRL 提交一条 GSM8K 数学样本。Bridge 将样本转换为 Episode，并发送给 Adapter Core。Server 控制并发，选择可用 Worker 并下发任务。Worker 调用当前策略模型生成答案，数学环境计算奖励并记录轨迹。Worker 将结果回报 Server，Server 校验并记录后再返回 VeRL，用于后续训练。

Server 怎样选择 Worker

Server 先过滤不合格的 Worker，再在合格 Worker 之间轮流选择。

环境支持Worker 必须支持请求指定的环境类型。
资源满足CPU、内存、GPU 和环境包等条件必须满足请求。
仍有容量Worker 当前执行中的任务数不能达到容量上限。
状态正常停止接收新任务、心跳超时或状态异常的 Worker 不会被选择。

异常、超时和重试

取消或超时

任务停止继续执行，迟到的结果不会覆盖已经确定的终态。

临时通信问题

连接中断、模型服务暂时不可用或暂时没有容量时，可以按配置重试。

环境执行失败

确定性的环境失败通常直接返回，不会自动换一个 Worker 再执行一次。

高级 Agent 路径

普通任务使用 Native Worker。只有请求明确选择 Agent 模式时，Server 才会使用下面的高级路径。

路径适用任务主要执行资源
Native Worker普通问答、环境交互和评测任务Worker 与环境插件
SWE Agent需要代码仓库和隔离运行环境的软件工程任务Agent 与 Worker Runtime Gateway
Code Agent使用工具完成多步代码操作的任务ToolEnv Agent

状态是否会保存

持久化是可配置能力。启用后，Server 会保存 Episode、任务分发和最终状态，并在 Adapter Core 进程重启后恢复可恢复的信息。关闭持久化时，这些运行状态只保存在内存中，进程退出后不会保留。

RS

uenv-worker

环境执行与实例运行时

uenv-worker 是部署在执行节点上的独立进程。它向 Server 注册本机能力并持续发送心跳，同时开放 gRPC 地址供 Server 下发 Episode；收到任务后，Worker 在本机创建或复用环境实例，完成模型生成、环境交互、奖励计算和结果回报。

Worker 与 Server 有两个通信方向Worker → Server：注册、心跳和最终结果回报。Server → Worker：根据注册时上报的地址调用 DispatchEpisode。因此本机绑定地址和 Server 实际回连的地址是两个概念。

先认识三个概念

名称含义
环境插件实现环境 reset / step / close 的本地程序。Worker 通过插件目录中的 Manifest 找到启动入口。
环境实例插件启动后可执行一个或多个 Episode 的运行实例，具有自己的状态和生命周期。
实例池保存可复用实例的本地池。池中没有可用实例时才创建新的实例，任务完成后再决定复用或回收。

一个 Episode 在 Worker 内怎样运行

1

建立双向联系

Worker 向 Server 注册环境类型、资源、容量和回连地址，并用心跳维持可用状态；Server 根据这个地址把 Episode 发回 Worker。

2

接纳任务

Worker 校验 Episode、调度租约和重复请求，再申请本机并发名额。全局并发由 Server 控制，本机并发由 Worker 再限制一层。

3

取得环境实例

Worker 优先复用实例池中的空闲实例；没有可用实例时才启动插件进程。实例可以按需创建，也可以在 Worker 启动时预热。

4

执行模型—环境循环

模型根据当前观测生成 action，插件执行 step 并返回新观测和奖励；循环持续到环境结束、达到步数限制或发生错误。

5

回报结果并处理实例

Worker 在执行期间报告进度，完成后把奖励、轨迹和结束状态单独回报 Server。回报暂时失败的结果写入 WAL，连接恢复后重放；环境实例则返回池中或被关闭。

Worker 与 Hub 的边界

Hub 提供环境版本和制品信息，Worker 负责执行。元数据查询和制品同步也不是同一个动作：

场景当前行为
普通插件环境Worker 从本地插件目录加载程序和 Manifest；启用 Hub 后，可以在启动或首次创建实例前拉取环境元数据，但不会为每个 Episode 下载插件。
EnvPackage / SWE 制品部署流程先从 Hub 下载并校验到节点目录，Worker 随后读取这些本地文件。同步不属于 Episode 执行过程。
职责边界Worker 只执行 Server 已分配的任务，不决定全局调度，也不维护环境版本的权威信息。SWE 容器与 Runtime Gateway 属于可选高级路径，不等同于上面的普通插件执行流程。
RS

uenv-hub

环境元数据与制品管理

uenv-hub 是独立部署的环境注册中心。它通过 HTTP API 和 uenv CLI 管理环境版本、接口定义、EnvPackage、Agent Bridge 与 Episode Stack；元数据保存在 SQLite，随包发布的制品保存在配置的 artifact 目录。

Hub 不在 Episode 的实时执行链路中发布、版本解析和制品同步通常发生在部署或启动阶段。Episode 开始后，Hub 不选择 Worker，不调用模型，也不接收训练结果。

先区分三个基础对象

对象保存的内容主要用途
Environment Manifest环境名称、版本、运行入口、资源需求、配置 Schema、接口 Schema、示例和 rubric。让 Server、Worker 和工具理解一个环境版本提供什么能力。
EnvPackage平台要求、Worker overlay、制品列表、下载地址、大小和 SHA-256 摘要。把 Worker 或 Agent 节点需要的文件作为一个可验证版本整体同步。
ArtifactEnvPackage 中的具体文件，例如 catalog、配置、规则文件或镜像 tar。由 CLI 下载并校验，避免节点使用不一致的制品。
Agent 路径还有两个组合对象Agent Bridge 固定 Agent scaffold 的版本；Episode Stack 再把环境、Agent scaffold、Runtime Gateway 和 EnvPackage 组合成一套可验证的启动计划。初次理解普通 Worker 路径时可以先跳过它们。

元数据和制品如何流动

1

发布

环境作者提交 Manifest、接口 Schema 或 EnvPackage。Hub 先校验结构和引用关系，再把版本元数据写入 SQLite，把制品写入 artifact 存储。

2

解析

调用方可以使用精确版本、latest 或版本约束查询。Hub 将它解析为确定版本，并返回对应 Manifest 或同步计划。

3

同步

节点按同步计划下载文件并校验 SHA-256 摘要，得到内容确定的本地目录。Worker 或 Agent 运行时读取该目录，而不是在每个 Episode 中临时取包。
